# 4D5307E6 — Halo 3

**Role in this project: the hard case.** Boots, runs, and renders environments
correctly, but character/geometry models collapse. It has driven most of the GPU
work in this fork, and the collapse is now believed **not to be our bug** (see
below).

- ISO: `/sdcard/Download/360/Halo 3.iso`
  (`content://media/external/downloads/1000069042` on the Odin 2)
- Per-game driver: **Turnip v26.0.0 R8** (`vulkan.ad07xx.so`), set via the
  per-game driver picker. The stock Qualcomm driver mis-compiles
  `resolve_full_32bpp` and produces a flat-navy main menu.

## Status (2026-08-02)

**Loads and runs.** Opening cinematic renders with correct models, textures and
water. **Character models still collapse ("the ball") in gameplay** — unchanged.

## ★ The collapse is almost certainly NOT this fork's bug

Three independent data points:

1. **The desktop RADV oracle renders Halo 3 correctly** — same Xenia lineage,
   different GPU driver.
2. **XenDroid fails it too** (2026-08-01, user-confirmed) — an unrelated
   third-party Android fork, on the same device.
3. It reproduces on **every** Adreno driver tried: stock, Turnip a7xx, Turnip
   a6xx.

⇒ The defect is **Adreno-side**, not in AE's engine. Effort spent diffing AE
against upstream to find "what we broke" is misdirected; the productive question
is what the Adreno driver does differently with the memexport path.

Deep dives, kept for the shader-level detail:
[`../HALO3_DETECTIVE_LOG.md`](../HALO3_DETECTIVE_LOG.md) (T1–T15, test → result
→ ruled in/out) and [`../HALO3_MENU_INVESTIGATION.md`](../HALO3_MENU_INVESTIGATION.md).

Mechanism as understood: Xenos **MEMEXPORT** (render-to-vertex-buffer skinning).
A producer VS (`9EA48FC2B26C325D`) scatter-compacts vertices; a consumer VS
(`488D9488AB7ED7D8`) reads `slot = floor(vtxIndex / c78.x)` and expands them.
Adreno underfills the produced buffer, the consumer reads zeros, and every vertex
lands on one point — the "ball". Memexport itself is proven correct end-to-end;
the open question is **why Adreno underfills**.

## 2026-08-02 — regression test after the v0.3.0 engine changes

Required because `xma_decoder` was changed from `"old"` to `"new"`, which affects
**every title using XMA audio** (see
[`../ENGINE_CHANGE_LOG.md`](../ENGINE_CHANGE_LOG.md)).

| check | result |
|---|---|
| Boots and reaches gameplay | ✅ unchanged |
| Errors in log | **0** |
| `MAIN_THREAD` CPU | 106 ticks/6s — **not** pegged (contrast NFS's stuck-audio signature) |
| **`XMA Decoder`** | **85 ticks/6s — actively decoding** |
| `RENDER` thread | 655 ticks/6s — busy, as expected |
| Rendering | opening cinematic correct: models, armour, textures, water |
| Character collapse | **still present, unchanged** |

⇒ **No regression, and no accidental fix.** `xma_decoder=new` and
`headless=true` are both safe for this title. This is the outcome a regression
test wants: the changes moved nothing here in either direction.

## Hardware requirements (as of 2026-07-25, expected to improve)
- **Adreno 700-series** currently needed. On Adreno 610 the GPU hard-hangs
  (`VK_ERROR_DEVICE_LOST`) on all three drivers tried.
- Phrase publicly as "currently", **not** a flat "7-series minimum" — the 610 is
  the weakest 600-series part and runs other titles fine (NFS Carbon was proven
  on it first).
